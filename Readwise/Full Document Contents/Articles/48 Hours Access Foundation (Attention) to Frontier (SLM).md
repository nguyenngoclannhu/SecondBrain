#### Foundation: Attention

[![](https://substackcdn.com/image/youtube/w_728,c_limit/l_youtube_play_qyqt8q,w_120/Fj3vOlaD71Y)](https://substack.com/redirect/7f802d44-c950-484b-b7db-e6c572271659?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI_zv_M4N2A50pyRXMoP1g)

This week’s **Foundation seminar** focused on rebuilding intuition for **attention**, starting from the famous paper *Attention Is All You Need*, which introduced the Transformer and reshaped how modern language models are built.

I began by framing tokens as vectors—units of information—and explained attention as a way to produce new tokens by combining existing ones with different weights. Each output token is simply a weighted mixture of earlier tokens, not a mysterious operation.

We then walked through **scaled dot-product attention** step by step. Tokens are projected into queries, keys, and values; dot products compare what a token is looking for with what others can provide; scaling keeps the numbers stable; and softmax turns scores into probabilities. I emphasized that matrix multiplication is just many dot products happening in parallel.

From there, we extended the idea to **multi-head attention**. Instead of one comparison space, multiple heads run in parallel, each learning a different way to relate tokens. Their outputs are concatenated and projected back to the original dimension so the next layer can proceed cleanly.

The main takeaway was simple: attention looks intimidating on paper, but once you unpack it, it’s a clear and systematic way to mix information across tokens—the core idea that makes Transformers work.

[![](https://substackcdn.com/image/fetch/$s_!qO3x!,w_550,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F32ef3ffa-5fa2-4499-933a-007706abce42_1650x1275.gif)](https://substack.com/redirect/bb436f12-7840-4de8-afd0-6e5f3cdc07da?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI_zv_M4N2A50pyRXMoP1g)#### Industry Insights

Between the two sessions, I took a moment to ask Xu a question: *“What are the biggest challenges in training production models at Amazon for a product used by a ton of customers?”* The last time I questioned her like this was at her dissertation defense many years ago. 😉😊

Drawing directly from her experience training production models, Xu outlined three recurring challenges she encounters when building language models in industry:

**Data quality dominates everything**

> Model performance is rarely limited by architecture—it’s limited by data. More data is not necessarily better. Noisy labels, inconsistent annotations, distribution mismatches, and overconfident synthetic responses can overwhelm the learning signal. Poor-quality data can push models toward unsafe behaviors, such as giving long, confident answers when ambiguity or clarification would be more appropriate.

**Benchmark metrics don’t match user experience**

> Offline metrics like loss, accuracy, or preference scores often fail to reflect what users actually care about. Models can improve on paper while becoming less helpful, less trustworthy, or less aligned in practice. This creates a persistent gap between academic-style evaluation and real-world usefulness, requiring more behavior-driven evaluation frameworks.

**Debugging failures is fundamentally hard**

> Language models rarely fail in obvious ways. Issues surface subtly—through hallucinations, overconfidence, or inconsistent reasoning—and the root cause can lie anywhere: data pipelines, prompts, training stages, evaluation design, or interactions across components. Debugging therefore requires careful, hypothesis-driven analysis across the entire system, not just the model itself.

As an educator, it’s rewarding when a student becomes your teacher. That was absolutely the case when Xu came back to share her real-world experience she’s gained working on the core AI team at Amazon. I couldn’t be more proud.

#### Frontier: Small Language Model & Agentic Tool Calling

This week’s Frontier seminar focused on **[small language models for efficient tool calling](https://substack.com/redirect/48691a26-d294-4016-aead-c5c294a0c78c?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI_zv_M4N2A50pyRXMoP1g)**—a recent paper that challenges the assumption that agents always need large models.

I began by setting the context: as agentic AI has taken off, we’ve seen growing evidence that smaller models can be effective when the task is *choosing tools*, not generating fluent text. The paper uses **OPT-350M**, an open GPT-style reference model from Meta, to show how big tech might approach this problem in practice.

We briefly revisited the OPT architecture—standard causal attention, feed-forward layers, and softmax decoding—and used it to explain why modern models became large in the first place: deeper stacks, Mixture-of-Experts, and huge vocabularies, not longer context windows.

The core idea is simple: for agent workflows, a large model can be overkill. If all the model needs to do is predict which tool to call and with what arguments, a compact model trained correctly can work just as well.

I walked through the training progression from pre-training, to instruction tuning, to tool-calling fine-tuning. Tool calling is still next-token prediction—but now the “right” tokens represent actions and parameters. I illustrated the full pipeline, from flattening message trajectories into a single sequence, through embeddings, projections, softmax, and cross-entropy loss.

The key technical insight is **masking**: during fine-tuning, loss is applied only to assistant tokens—the points where tool decisions are made. System and user tokens are ignored, which keeps training focused and efficient.

**The closing message:** this paper reframes how we should think about agents. Instead of defaulting to ever-larger models, it shows how narrowing the objective—tool selection over text generation—opens up a very different, and much more efficient, design space.

<h2 style="position: relative;font-family: 'SF Pro Display',-apple-system-headline,system-ui,-apple-system,BlinkMacSystemFont,'Segoe UI',Roboto,Helvetica,Arial,sans-serif,'Apple Color Emoji','Segoe UI Emoji','Segoe UI Symbol';font-weight: bold;-webkit-font-smoothing: antialiased;-moz-osx-font-smoothing: antialiased;-webkit-appearance: optimizelegibility;-moz-appearance: optimizelegibility;appearance: optimizelegibility;margin: 1em 0 0.625em 0;color: rgb(54,55,55);line-height: 1.16em;font-size: 1.625em;">Foundation: Attention</h2>
<a data-component-name="Youtube2ToDOMStatic" href="https://substack.com/redirect/7f802d44-c950-484b-b7db-e6c572271659?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI\_zv\_M4N2A50pyRXMoP1g" style="display: block;margin: 32px 0;" target="\_blank"><img src="https://substackcdn.com/image/youtube/w\_728,c\_limit/l\_youtube\_play\_qyqt8q,w\_120/Fj3vOlaD71Y" style="border: none !important;vertical-align: middle;-ms-interpolation-mode: bicubic;max-width: 100%;height: auto;margin: 0 auto;display: block;width: 100%;"/></a><p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>This week’s </span><strong>Foundation seminar</strong><span> focused on rebuilding intuition for </span><strong>attention</strong><span>, starting from the famous paper </span><em>Attention Is All You Need</em><span>, which introduced the Transformer and reshaped how modern language models are built.</span></p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">I began by framing tokens as vectors—units of information—and explained attention as a way to produce new tokens by combining existing ones with different weights. Each output token is simply a weighted mixture of earlier tokens, not a mysterious operation.</p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>We then walked through </span><strong>scaled dot-product attention</strong><span> step by step. Tokens are projected into queries, keys, and values; dot products compare what a token is looking for with what others can provide; scaling keeps the numbers stable; and softmax turns scores into probabilities. I emphasized that matrix multiplication is just many dot products happening in parallel.</span></p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>From there, we extended the idea to </span><strong>multi-head attention</strong><span>. Instead of one comparison space, multiple heads run in parallel, each learning a different way to relate tokens. Their outputs are concatenated and projected back to the original dimension so the next layer can proceed cleanly.</span></p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">The main takeaway was simple: attention looks intimidating on paper, but once you unpack it, it’s a clear and systematic way to mix information across tokens—the core idea that makes Transformers work.</p>

<h2 style="position: relative;font-family: 'SF Pro Display',-apple-system-headline,system-ui,-apple-system,BlinkMacSystemFont,'Segoe UI',Roboto,Helvetica,Arial,sans-serif,'Apple Color Emoji','Segoe UI Emoji','Segoe UI Symbol';font-weight: bold;-webkit-font-smoothing: antialiased;-moz-osx-font-smoothing: antialiased;-webkit-appearance: optimizelegibility;-moz-appearance: optimizelegibility;appearance: optimizelegibility;margin: 1em 0 0.625em 0;color: rgb(54,55,55);line-height: 1.16em;font-size: 1.625em;">Industry Insights</h2>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>Between the two sessions, I took a moment to ask Xu a question: </span><em>“What are the biggest challenges in training production models at Amazon for a product used by a ton of customers?”</em><span> The last time I questioned her like this was at her dissertation defense many years ago. 😉😊</span></p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">Drawing directly from her experience training production models, Xu outlined three recurring challenges she encounters when building language models in industry:</p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><strong>Data quality dominates everything</strong></p>
<blockquote style="border-left: 4px solid #0068EF;margin: 20px 0;padding: 0;"><p style="margin: 0 0 20px 0;color: rgb(54,55,55);margin-left: 20px;line-height: 26px;font-size: 16px;">Model performance is rarely limited by architecture—it’s limited by data. More data is not necessarily better. Noisy labels, inconsistent annotations, distribution mismatches, and overconfident synthetic responses can overwhelm the learning signal. Poor-quality data can push models toward unsafe behaviors, such as giving long, confident answers when ambiguity or clarification would be more appropriate.</p></blockquote>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><strong>Benchmark metrics don’t match user experience</strong></p>
<blockquote style="border-left: 4px solid #0068EF;margin: 20px 0;padding: 0;"><p style="margin: 0 0 20px 0;color: rgb(54,55,55);margin-left: 20px;line-height: 26px;font-size: 16px;">Offline metrics like loss, accuracy, or preference scores often fail to reflect what users actually care about. Models can improve on paper while becoming less helpful, less trustworthy, or less aligned in practice. This creates a persistent gap between academic-style evaluation and real-world usefulness, requiring more behavior-driven evaluation frameworks.</p></blockquote>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><strong>Debugging failures is fundamentally hard</strong></p>
<blockquote style="border-left: 4px solid #0068EF;margin: 20px 0;padding: 0;"><p style="margin: 0 0 20px 0;color: rgb(54,55,55);margin-left: 20px;line-height: 26px;font-size: 16px;">Language models rarely fail in obvious ways. Issues surface subtly—through hallucinations, overconfidence, or inconsistent reasoning—and the root cause can lie anywhere: data pipelines, prompts, training stages, evaluation design, or interactions across components. Debugging therefore requires careful, hypothesis-driven analysis across the entire system, not just the model itself.</p></blockquote>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">As an educator, it’s rewarding when a student becomes your teacher. That was absolutely the case when Xu came back to share her real-world experience she’s gained working on the core AI team at Amazon. I couldn’t be more proud.</p>
<h2 style="position: relative;font-family: 'SF Pro Display',-apple-system-headline,system-ui,-apple-system,BlinkMacSystemFont,'Segoe UI',Roboto,Helvetica,Arial,sans-serif,'Apple Color Emoji','Segoe UI Emoji','Segoe UI Symbol';font-weight: bold;-webkit-font-smoothing: antialiased;-moz-osx-font-smoothing: antialiased;-webkit-appearance: optimizelegibility;-moz-appearance: optimizelegibility;appearance: optimizelegibility;margin: 1em 0 0.625em 0;color: rgb(54,55,55);line-height: 1.16em;font-size: 1.625em;">Frontier: Small Language Model &amp; Agentic Tool Calling</h2>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>This week’s Frontier seminar focused on </span><strong><a href="https://substack.com/redirect/48691a26-d294-4016-aead-c5c294a0c78c?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI\_zv\_M4N2A50pyRXMoP1g" rel="" style="color: rgb(54,55,55);text-decoration: underline;">small language models for efficient tool calling</a></strong><span>—a recent paper that challenges the assumption that agents always need large models.</span></p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>I began by setting the context: as agentic AI has taken off, we’ve seen growing evidence that smaller models can be effective when the task is </span><em>choosing tools</em><span>, not generating fluent text. The paper uses </span><strong>OPT-350M</strong><span>, an open GPT-style reference model from Meta, to show how big tech might approach this problem in practice.</span></p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">We briefly revisited the OPT architecture—standard causal attention, feed-forward layers, and softmax decoding—and used it to explain why modern models became large in the first place: deeper stacks, Mixture-of-Experts, and huge vocabularies, not longer context windows.</p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">The core idea is simple: for agent workflows, a large model can be overkill. If all the model needs to do is predict which tool to call and with what arguments, a compact model trained correctly can work just as well.</p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">I walked through the training progression from pre-training, to instruction tuning, to tool-calling fine-tuning. Tool calling is still next-token prediction—but now the “right” tokens represent actions and parameters. I illustrated the full pipeline, from flattening message trajectories into a single sequence, through embeddings, projections, softmax, and cross-entropy loss.</p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>The key technical insight is </span><strong>masking</strong><span>: during fine-tuning, loss is applied only to assistant tokens—the points where tool decisions are made. System and user tokens are ignored, which keeps training focused and efficient.</span></p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><strong>The closing message:</strong><span> this paper reframes how we should think about agents. Instead of defaulting to ever-larger models, it shows how narrowing the objective—tool selection over text generation—opens up a very different, and much more efficient, design space.</span></p>
