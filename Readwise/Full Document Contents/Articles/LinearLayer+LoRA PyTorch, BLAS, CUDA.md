Why is it so confusing for people to understand something as simple as a linear layer — even for AI engineers who work in top AI labs? There are three main sources of confusion that make it hard for AI engineers to bridge the gap between math and implementation.

1. First, PyTorch **transposes the math** y=Wx+b to y=xW^T+b to match CUDA’s row-major layout.
2. Second, it **transposes again** for BLAS, which uses column-major order.
3. Third, it **transposes back** to row-major when adding the bias.

All three produce the same result but hide the simple math behind layers of memory optimization.

Let’s clear this confusion once for all!

In the **AI by Hand** ✍️ view, everything starts with the math. A linear layer is just a matrix where **rows are weights** (one per output unit) and **columns are feature vectors** (one per instance). When you multiply them, each cell in the output naturally represents the intersection between a weight row and a feature column. The shape of the output pops out visually: the number of **rows** equals the number of outputs, and the number of **columns** equals the batch size (or feature instances).

[![](https://substackcdn.com/image/fetch/$s_!irlz!,w_1100,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Ff61bdf5a-2260-41b0-b61c-892cb37f583d_842x630.png)](https://substack.com/redirect/aa142cc4-d1c7-4b01-8f07-6d8a8eb6f1f4?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI_zv_M4N2A50pyRXMoP1g)To handle bias elegantly, we can treat it as just another value in the weight matrix. Append a **1** to each input feature vector, making it one element longer. Now the bias term becomes part of the same matrix multiplication — no separate addition step needed. This small trick unifies “multiply” and “add bias” into a single, clean matrix operation that’s easy to see and compute by hand. I use this representation extensively in my teaching and research.

PyTorch transposes the usual math y=Wx+b to fit the way CUDA handles data in memory — the **first source of confusion**. In math, x is a column vector, but in PyTorch each input is stored as a row so its features are contiguous in memory. To keep things efficient on GPU, PyTorch uses y=xW^T+b— the same result as the textbook formula, just transposed to match CUDA’s row-major layout (though not BLAS’s).

[![](https://substackcdn.com/image/fetch/$s_!SUAI!,w_1100,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2Feee65421-2386-4328-90b6-6c955852cecd_1470x962.png)](https://substack.com/redirect/fc20eee2-55a8-4c8c-aec0-c02644fc4b63?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI_zv_M4N2A50pyRXMoP1g)👇 Scroll to the bottom to download this Excel Blueprint. [![](https://substackcdn.com/image/fetch/$s_!-dwi!,w_1100,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F40f6d934-7e80-44b2-9256-a09e4a065a7d_1586x1242.png)](https://substack.com/redirect/e62b163a-7686-4df4-9d5a-e5f6ff1729a3?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI_zv_M4N2A50pyRXMoP1g)Under the hood, PyTorch transposes things yet again when it calls into BLAS libraries — a **second source of confusion**. BLAS was designed for Fortran, which uses **column-major** order, while PyTorch (like C and CUDA) uses **row-major** order. To make the math line up, PyTorch silently flips the operands so BLAS sees the data in the format it expects. This hidden transpose doesn’t change the result, but it adds another layer of indirection — the second transpose — between the mathematical view and how the computation actually runs in memory.

[![](https://substackcdn.com/image/fetch/$s_!VPRd!,w_1100,c_limit,f_auto,q_auto:good,fl_progressive:steep/https%3A%2F%2Fsubstack-post-media.s3.amazonaws.com%2Fpublic%2Fimages%2F39769f86-8a8b-46e9-9cfa-8f0e1817355b_1466x1006.png)](https://substack.com/redirect/f028940b-d841-4b8a-9214-c44ed86f3f59?j=eyJ1IjoiNnE2ZWdsIn0.JeUaI03hkTZe3g0Y-WbKcpI_zv_M4N2A50pyRXMoP1g)Then, when PyTorch goes back to CUDA to add the bias through broadcasting, comes the **third source of confusion** — yet another transpose back to **row-major**. After BLAS finishes in column-major order, the result has to be viewed again in CUDA’s row-major layout so that the bias can be added element-wise across rows. This final flip doesn’t change the math, but it restores the data layout PyTorch expects for tensors, completing a full loop of transposes: math → PyTorch → BLAS → CUDA → PyTorch.

<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">Why is it so confusing for people to understand something as simple as a linear layer — even for AI engineers who work in top AI labs? There are three main sources of confusion that make it hard for AI engineers to bridge the gap between math and implementation.</p>
<ol style="margin-top: 0;padding: 0;">
<li style="margin: 8px 0 0 32px;"><p style="color: rgb(54,55,55);line-height: 26px;margin-bottom: 0;box-sizing: border-box;padding-left: 4px;font-size: 16px;margin: 0;"><span>First, PyTorch </span><strong>transposes the math</strong><span> y=Wx+b to y=xW^T+b to match CUDA’s row-major layout.</span></p></li>
<li style="margin: 8px 0 0 32px;"><p style="color: rgb(54,55,55);line-height: 26px;margin-bottom: 0;box-sizing: border-box;padding-left: 4px;font-size: 16px;margin: 0;"><span>Second, it </span><strong>transposes again</strong><span> for BLAS, which uses column-major order.</span></p></li>
<li style="margin: 8px 0 0 32px;"><p style="color: rgb(54,55,55);line-height: 26px;margin-bottom: 0;box-sizing: border-box;padding-left: 4px;font-size: 16px;margin: 0;"><span>Third, it </span><strong>transposes back</strong><span> to row-major when adding the bias.</span></p></li>
</ol>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">All three produce the same result but hide the simple math behind layers of memory optimization.</p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;">Let’s clear this confusion once for all!</p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>In the </span><strong>AI by Hand</strong><span> ✍️ view, everything starts with the math. A linear layer is just a matrix where </span><strong>rows are weights</strong><span> (one per output unit) and </span><strong>columns are feature vectors </strong><span>(one per instance). When you multiply them, each cell in the output naturally represents the intersection between a weight row and a feature column. The shape of the output pops out visually: the number of </span><strong>rows</strong><span> equals the number of outputs, and the number of </span><strong>columns</strong><span> equals the batch size (or feature instances).</span></p>

<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>To handle bias elegantly, we can treat it as just another value in the weight matrix. Append a </span><strong>1</strong><span> to each input feature vector, making it one element longer. Now the bias term becomes part of the same matrix multiplication — no separate addition step needed. This small trick unifies “multiply” and “add bias” into a single, clean matrix operation that’s easy to see and compute by hand. I use this representation extensively in my teaching and research.</span></p>
<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>PyTorch transposes the usual math y=Wx+b to fit the way CUDA handles data in memory — the </span><strong>first source of confusion</strong><span>. In math, x is a column vector, but in PyTorch each input is stored as a row so its features are contiguous in memory. To keep things efficient on GPU, PyTorch uses y=xW^T+b— the same result as the textbook formula, just transposed to match CUDA’s row-major layout (though not BLAS’s).</span></p>

<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>Under the hood, PyTorch transposes things yet again when it calls into BLAS libraries — a </span><strong>second source of confusion</strong><span>. BLAS was designed for Fortran, which uses </span><strong>column-major</strong><span> order, while PyTorch (like C and CUDA) uses </span><strong>row-major</strong><span> order. To make the math line up, PyTorch silently flips the operands so BLAS sees the data in the format it expects. This hidden transpose doesn’t change the result, but it adds another layer of indirection — the second transpose — between the mathematical view and how the computation actually runs in memory.</span></p>

<p style="margin: 0 0 20px 0;color: rgb(54,55,55);line-height: 26px;font-size: 16px;"><span>Then, when PyTorch goes back to CUDA to add the bias through broadcasting, comes the </span><strong>third source of confusion</strong><span> — yet another transpose back to </span><strong>row-major</strong><span>. After BLAS finishes in column-major order, the result has to be viewed again in CUDA’s row-major layout so that the bias can be added element-wise across rows. This final flip doesn’t change the math, but it restores the data layout PyTorch expects for tensors, completing a full loop of transposes: math → PyTorch → BLAS → CUDA → PyTorch.</span></p>
